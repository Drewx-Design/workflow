# Kimi scope review: why I kept it

[Workflow method](../compound-engineering/README.md) · [Notes index](README.md)

On November 12, I kept Kimi as an advisory scope reviewer and added a planning-stage check. The initial checkpoint showed that it could find specific interface omissions and additions after the other reviews had finished.

## The checkpoint

The checkpoint covered five counted UI PR reviews from November 5–10. On four of those PRs, the reviewing host confirmed at least one finding that the other reviewers on that PR had missed. The host checked each finding against the agreed plan or issue and the source. This count is PRs with a verified unique finding, not the proportion of flags that were correct.

The five reviews covered document history, export, workspace controls, navigation, and a draft selection bar. Some were attended sessions. The other reviewers available on each PR varied, so this is a record of a small workflow trial rather than a controlled comparison of models.

Examples, with private issue identifiers omitted:

| Observed mismatch | What happened after verification |
| --- | --- |
| A Download button disappeared after a failed check, although the agreed interface called for a visible disabled button. | The disabled state was implemented. |
| A document-history change omitted a required focus disclosure. | The omission was corrected. |
| A navigation change treated a system-driven composer opening as a user gesture, which could release the current interaction state. | The write was corrected to identify it as a system action. |

About half of the checkpoint's flags were rejected after verification. Host verification took approximately 1–12 minutes per run. These were source reviews; the findings themselves did not establish that the interface worked in a browser.

## How I use it now

Kimi checks substantial UI plans against the request before implementation, and checks final UI changes against the plan or issue after review and fixes. It identifies unrequested controls, messages, states, or behavior and missing required elements. The host confirms or rejects each finding; product decisions stay with me.

Later runs through November 13 have been mixed: some found no unique issue, one flagged server work omitted from its UI-only packet, and a plan review found missing inventory mappings. I use that feedback to make the review packet explicit about what it includes and which product decisions I have already confirmed.

I will review usefulness after ten more counted runs, tracking unique confirmed findings, false flags, and verification time. The result so far supports a narrow advisory role in my workflow. It does not measure reduced production defects or time saved.

Source: my private calibration records and the November 12 decision, summarized and checked on November 13. The five counted runs are identified by their reviewed changes; not-run entries are excluded. Raw packets and private project details are not included.
